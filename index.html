2026 · Property management

MCP server for live operations data

Properties, units, vendors, staff, incidents and tasks lived inside an internal .NET app. AI assistants could see none of it.

What I built
A Model Context Protocol server in C# on .NET 8 with read-only tools for properties, units, vendors, staff, incidents and tasks, plus context resources (a data dictionary, conventions and a glossary). Runs over stdio for desktop clients and HTTP for hosted ones.
Key decision
It calls the platform's existing API with a scoped key instead of reaching into the database, so it inherits the app's rules. The resources exist because a model given only field names guesses at meaning, and that is where it makes things up.
Result
The first tool call was timing out mid-conversation. I traced it to a heavy endpoint built for a different purpose, added a lean one for AI use and a short cache, and the tools became usable in live conversation.

2026 · Leasing & collections

Agent-ready API for a partner's AI agent

An outside company's AI agent needed leasing and resident data from the property-management system to run prospect and collections follow-ups.

What I built
A versioned, read-only API covering prospects, tenants, transactions, unit status and more, with a discovery manifest, schema endpoint, paging guards and an integration guide for the partner's developers.
Key decision
"Do not contact" lives in staff free-text notes. Agreed markers set a hard stop flag in code; a looser list of candidate terms surfaces notes for the agent to judge, and only that list can change without a release. Column choices are enums, so injection has nothing to work with.
Result
The full specification delivered, every field checked against the vendor's data dictionary and the live database, with contract and behaviour tests so the API cannot quietly drift from what the partner was promised.

2026 · Security In progress

Per-client API keys for AI and integration consumers

Keys for the MCP server, an automation platform and the AI partner lived in a config file committed to the repository. Changing or revoking one meant a code change and a redeploy.

What I'm building
Hashed per-client keys in the database, scopes per endpoint, and a lockout after repeated failures. Old and new keys work side by side during rollout, so no integration has a flag day.
Why the tests mattered
Unit tests caught that the existing key would have been refused on every endpoint at deploy. It was fixed before it reached a server.

How I work

Spec first, tested, owned to production

  1. Agree before building

    I use a spec-driven AI workflow with Claude Code. Requirements, design and the test plan are written and approved before any code is generated.

  2. Test where it would hurt

    Authentication, schedulers and API contracts get unit tests. Those tests have stopped real defects from reaching production.

  3. Own it end to end

    I write the requirements, the SQL, the code and the tests, deploy to test and live, and add the monitoring that shows whether it is still working.
